# Frontend conventions

SvelteKit 5 (runes) + Tailwind v4, talking to the FastAPI backend in `../backend`.

## Where code goes

- `src/lib/api/` — `schema.ts` (generated), `wrapper.ts`, and one adapter per backend router in `*/adapters/`.
- `src/lib/components/` — styled UI with no API calls and no business logic.
- `src/lib/features/<feature>/components/` — feature components.
- `src/routes/` — pages: load data, render feature components, pass them callbacks.

Move something into `components/` once it has been copied three times.

## API types come from the backend

- `src/lib/api/schema.ts` is generated by `npm run gen:api` with the backend running on port 8000. Regenerate after any Pydantic model or route change, run `npm run check`, and fix every call site it reports. Commit `schema.ts`.
- Import request/response types from `$lib/api/schema`. Filter types are derived in the adapter from `operations[...]['parameters']['query']` (see `adapters/children.ts`).
- Value lists for dropdowns come from the generated `*Values` arrays (e.g. `australianStateValues`). Types the backend doesn't send live in `features/<feature>/types.ts`.
- Adapter methods call `apiWrapper<T>(url, { method, body, fetcher })`. It toasts `msg` on every non-GET and turns a 422 into `fieldErrors` keyed by field name.

## Validation lives on the server

Pydantic is the validator. Forms use HTML attributes (`required`, `type`, `minlength`, `maxlength`) plus only the cross-field checks the server can't see, such as confirm-password.

## Dates are strings

Dates stay as ISO strings end to end: `YYYY-MM-DD` for dates, ISO datetimes for timestamps. Compare them as strings and format only for display (`DataCard` `format: 'date' | 'datetime'`, `utils/helpers.ts`). Converting to `Date` objects caused off-by-one-day bugs in UTC+10.

## Pages own data, components own UI state

- Reads: `+page.ts` / `+layout.ts` `load` functions, passing SvelteKit's `fetch` into the adapter and tagging with `depends('app:...')`.
- Writes: the page calls the API and passes a callback down. Components receive data and callbacks as props. The one exception is a self-contained widget reused across pages with no page-specific behaviour.

### Forms

One component per form, taking `onsubmit: SubmitHandler<T>` (`$lib/types/forms`). The page calls the API, handles success (redirect, refresh) and returns the response. The form owns `body`, `errors` and `isLoading`, sets `errors = response.fieldErrors`, and resets `body` when `response.ok`. Reference pair: `features/auth/components/LoginForm.svelte` + `routes/[location_code]/(public)/login/+page.svelte`.

Each input is `<Field label error>` wrapping a native element that takes the snippet's `id`. `routes/layout.css` already styles native inputs, selects and textareas.

### Tabs

`TabbedPanels` takes `tabs: { id, label }[]` and a `panel(id)` snippet, so panel props are type-checked. Tab ids live in `navigation/tabs.ts`.

## UI conventions

These keep features looking like one app. They're written for the customer-facing pages; the admin UI can be plainer but uses the same components.

### Mobile first

- Customers use phones; admin uses desktop. Design every customer screen for a ~375px-wide phone first, then let it widen. Write the base classes for mobile and add `md:` only to make things nicer on desktop, never the other way round.
- Tap targets are at least 44px tall (`Button` is 48px). This applies to calendar cells, chevrons, tiles and chips too.
- Nothing may depend on hover: hover effects are extras, and every state must be visible without them.
- Inputs stay at `text-base` (16px) so iOS doesn't zoom in on focus, and keep `type`/`inputmode`/`autocomplete` set so the right keyboard appears.
- Check every customer change at 375px before desktop.

### Colour

- Use the tokens in `routes/layout.css` only: no Tailwind palette colours (`gray-*`, `slate-*`, hex values) in components. Tenant branding works by swapping `--primary`, so anything hard-coded escapes it.
- `--primary-hover`, `--primary-soft` and `--hyperlink*` are derived from `--primary` in `layout.css`; never set them per component.

### Page structure

- Every customer page is `<Page>` → `<PageHeader>` → content (`components/layout/`).
- `Page` is centred. Customer pages are always `narrow` (`max-w-xl`): one column on every screen, so desktop sees the same layout centred. `wide` is for admin pages only.
- `PageHeader` takes `title` (sentence case), optional `eyebrow` (e.g. "Step 2 of 3"), `description` and an `actions` snippet.
- Customers navigate with `BottomNav` on mobile and the sidebar on desktop; staff and admin use the sidebar (drawer on mobile).
- Every page has the site's header (`Header` in the tenant `Layout`'s `header` snippet; `PlatformHeader` on the platform's own site), logins and error pages included. The one exception is the kiosk tablet (`/{location}/kiosk`), which families and staff use in person and mustn't navigate away from.

### Public site pages

The business's pages (`/`, `/locations`, `/about`: the `routes/(site)` group, whose layout holds the header, footer and colours) and a centre's own page (`/{location}`, later `/{location}/programs`) are the public site (`docs/public-site.md`), laid out differently from customer pages:

- The tenant `Layout` gets `flush` (no padding) and the page is a stack of `SiteSection` bands: full width, content in a `max-w-6xl` column, alternating `tone` (`plain`, `muted`, `tint`). No `Page`/`PageHeader`.
- Each band's heading is `SiteHeading`; the hero's headline is an `h1` with `display-text`. Both text roles are defined in `layout.css`.
- Still mobile first: one column on a phone, grids (`md:grid-cols-2`, `lg:grid-cols-3`) only from `md`.
- Colours: `--primary` for actions, `--secondary-soft` for tinted bands, `--accent` only as decoration (bars, icons), never for text, since a business may pick one too light to read. Never `--secondary` or `--accent` at full strength behind text.
- A hero's buttons go in `<ActionBar start>`: together on the left, main action first, from `md`.
- Page text is edited where it's shown, never in a settings screen: wrap each editable part in `EditableSection` (`canEdit` from the page's data, the view as its children, an `editor(done)` snippet holding an ordinary form with `oncancel={done}`). The page saves, invalidates its data and calls `done()`. Editing is desktop only; an empty section shows its editor a prompt and everyone else nothing (`SiteSection desktopOnly` for a band that would otherwise be empty on a phone).

### Surfaces

- `Card` is the only surface. It has default padding; don't add your own `p-*` to it (cards whose rows run edge to edge, like `DataCard` or the per-child sections in `ReviewBooking`, pass `padded={false}`). No bordered card inside another card: a list of cards is a plain `flex flex-col gap-4`.
- Radius: `rounded-2xl` surfaces, `rounded-lg` buttons and tiles, `rounded-full` dots and pills. Nothing else.
- Spacing: `gap-6` between page sections, `gap-4` inside a card.

### Tables

- Every table uses a shared component, never hand-built rows: `GridTable` (`components/layout/`) for lists read across (run sheets, staff, service days), `DataTable` for lists whose rows open a detail page (cards on a phone).
- Rows are a fixed height (`ROW_HEIGHT_REM`, room for a 48px button): each cell is one line, vertically centred, cut off with "…". A tick, dash, pill or button never changes a row's height, and columns always line up.
- Long lists get `maxRows` (a fixed height that scrolls, headers pinned); on a phone the table scrolls sideways inside itself, never the page.

### Text

| Role | Classes |
|---|---|
| Page title | `text-2xl font-extrabold text-(--text)` (via `PageHeader`) |
| Public site hero / band title | `display-text` / `headline-text` (via `SiteHeading`); public site pages only |
| Section title | `text-lg font-extrabold text-(--text)` |
| Label (fields, data rows, card titles, eyebrows, filters, table headers) | `label-text` (`text-xs font-extrabold uppercase tracking-wide text-(--text-muted)`, defined once in `layout.css`) |
| Body | `text-base text-(--text)`; values `font-semibold` |
| Secondary | `text-sm text-(--text-muted)` |

Only `font-semibold` and `font-extrabold`; no `font-medium` or `font-bold`.

### Shared text components

Each text role has one look, set by a component, never by hand-written classes (`components/text/`, `components/forms/`):

| Role | Use |
|---|---|
| Section title (+ one-line description, actions beside it) | `SectionHeading` (`details` snippet when the description needs markup) |
| A label on its own (a filter, a list's heading, an eyebrow) | the `label-text` class |
| Label and value pairs (value semibold, "—" when empty) | `LabelValueList` |
| Nothing to show ("No bookings yet.") | `EmptyState`: secondary text, left-aligned |
| An error (a field's or an action's) | `ErrorText` (`Field` uses it via `InlineError`) |
| How things stand, in a coloured box | `Notice` with a `tone` |
| A status badge | `Pill` with a `tone` |
| A checkbox with a title and help line | `CheckboxRow` |
| A modal's intro line | `Modal`'s `description` |
| A compact data card's title | `TitleCard` (the label role); cards a page is built from use `SectionHeading` |

- Form labels are `Field`'s (`.field-label`, the label role). A plain `<label>` wrapping a checkbox or filter has no styling of its own, so the text inside it keeps its role.
- The kiosk tablet is read at arm's length: these components take `size="kiosk"` (one size up; empty states centred) instead of kiosk copies. Kiosk screen titles are `text-3xl`, section titles `text-xl`, subtitles `text-lg` muted, body `text-lg`. A kiosk component also shown on the website (e.g. `StaffRoll` on the admin run sheet) takes a `size` prop and passes it down.

### Actions

- In features and routes, every action is a `Button`. Raw `<button>` only for selectable tiles (service cards, child chips) and calendar cells and their prev/next arrows, styled with tokens and at least 44px. Components in `components/` may use raw elements internally (e.g. `MultiSelect`'s options); that's what they're for.
- `default` for the main action (one per view), `ghost` for secondary (Back, Cancel). Buttons are uppercase (applied by `Button`).
- A row of actions goes in `ActionBar`, secondary first and main action last. On mobile the buttons stack full width with the main action at the bottom, nearest the thumb; from `md:` they sit in one row, secondary left and main right. Buttons inside it size themselves; don't pass `fullWidth`.
- In multi-step flows (booking), use `<ActionBar sticky>` so Continue stays reachable on long pages.
- Links use `HyperTextLink`: 44px tall by default ("Back to bookings", "Forgot your password?"); `inline` only inside running text. `Button variant="hyperlink"` is for a button that looks like a link (e.g. "Show more"), not for navigation.
- Yes/no questions use `confirmAction()` (see Confirmations below). `Modal` (a bottom sheet on mobile) is only for small forms or extra content over a page, with its buttons in `actions`. Navigation menus use `Drawer` (staff and admin only).

### Confirmations

Every "are you sure?" goes through `confirmAction()` from `components/overlays/confirm.svelte`. It's shown by the one `ConfirmDialog`, already mounted in the tenant layout (`routes/[location_code]/+layout.svelte`), so a page only calls the function: no `Modal`, no `bind:this`, no open/close or loading state of its own. Never use `window.confirm`.

A destructive action (cancel, refund, remove), with the work passed as `action`:

```ts
import { confirmAction } from "$lib/components/overlays/confirm.svelte";

async function removePickup() {
    await confirmAction({
        title: `Remove ${pickup.first_name}?`,
        message: `${pickup.first_name} will no longer be able to collect your children.`,
        confirmLabel: "Remove",
        tone: "danger",
        action: async () => {
            const response = await pickupsApi.deactivate(pickup.id);

            if (response.ok) {
                await invalidate("app:customer-account");
                await goto(accountPickupsHref);
            }
        },
    });
}
```

A check before continuing, with no `action` (the page carries on itself):

```ts
if (!(await confirmAction({ title: "Their ID will need checking again", message, confirmLabel: "Save changes" }))) {
    return;
}
```

- `title` is a question or consequence in sentence case; `message` says what happens (what's released, refunded or reset); `confirmLabel` repeats the verb ("Remove", "Refund", "Cancel booking"), never "OK" or "Yes".
- `tone: "danger"` for anything destructive: red confirm button, and the cancel button reads "Keep". Otherwise it reads "Cancel". Override with `cancelLabel` only if neither fits.
- With `action`, the confirm button shows a spinner and the dialog can't be dismissed until it finishes; then it closes. Do the follow-up (refresh, navigate) inside `action`. API errors already toast from `apiWrapper`, so the action doesn't need to report them.
- It resolves `true` once confirmed (and the action has finished), `false` for cancel, Escape or tapping outside.
- Reference uses: the review page (cancel booking, refund), child page (remove child), pickup edit page (remove, ID re-check).

### Tabs

`TabbedPanels` takes `tabs: { id, label }[]` and a `panel(id)` snippet, so panel props are type-checked. Tab ids live in `navigation/tabs.ts`. Nothing scrolls sideways: up to 3 tabs share the row equally (labels may wrap, so keep them to one or two words); with more, mobile gets a native select. Customer pages use at most 3 tabs; a page with more sections uses a list of 44px link rows to separate pages instead.

### Forms

`Form` + `Field` with native inputs (see "Forms" above). Inputs are underline-only, styled globally in `layout.css`; don't restyle them.

### Words and formats

- Write all copy in sentence case, even where CSS uppercases it ("Book now", "Add a child"). Australian spelling ("Authorised").
- Customer dates use `utils/helpers.ts`: `formatDate` → "Tue, 20 Oct", plus the year when it isn't this year ("Mon, 20 Oct 2025"); `formatDateRange` → "Tue, 20 Oct – Fri, 24 Oct"; `formatTimestamp` for timestamps, same format. DD/MM/YYYY (`formatDateDDMMYYYY`) only in admin tables.
- Money: `formatMoney(cents, currency)`. Never format inline.
- Session times: `formatTimeRange(start, end)` → "3:00pm – 6:00pm" (`formatTime` for one). They're in the location's timezone; show them as sent, never convert.
- Service policies (ages, refund window, late fee) are worded only by `features/services/policies.ts`, so every screen says the same thing. Addresses and the maps link come from `features/location/address.ts`; the centre's details are shown with `CentreCard`.
- Status wording comes from one map per feature, not per component.

### Shared components

Before using a component in `components/` that no feature uses yet, bring it up to these conventions first.
